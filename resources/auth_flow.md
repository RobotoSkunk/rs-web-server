# Authentication Flow
If you wonder why the f*** I'm leaving the entire administration code of my
website open sourced, the reason is because I don't want to rely on the
traditional "security by obscurity" method, and this entire website has served
me as a good practice for modern web development.

If you think that I'm doing something really wrong with the security
implementation of my own website, please send me an email
(contact@robotoskunk.com).


## Registration
The users can only be registered via `bun admin:create`. The server will ask for
a unique username and a password (it should be randomly generated with a secure
cryptographic algorithm).


## Authentication Steps
The authentication should not last more than 5 minutes or the authentication
flow will be reset.

### Step 1: Handshake
The client sends to the server the following values:
- The administrator username.
- The public client ephemeral from the 'secure-remote-password/client' library.

The server stores the authentication identifier and the public client ephemeral,
then it answers with the following:
- The server ephemeral public from the 'secure-remote-password/server' library.
- The SRP model salt from the database.
- The administrator's unique salt from the database.

If the username doesn't exist, the server has to generate two bland values
and return it to the client. The two values are suggested to be generated from
the given username and two random secure bytes generated by the server and
stored in memory.

```txt
bland_salt: hmac256(bland_salt + username)
bland_srp_salt_public: hmac256(bland_srp_salt + username)
bland_server_ephemeral_public: hmac256(bland_ephemeral_salt + username)
```

The two bland salts should be stored securely, so its value persists between
server restarts.

### Step 2: Authorization
The client takes the given server public ephemeral and salt to derivate a
private key and a derivated session. Then, sends the client session proof to
the server.

The server takes the client session proof and derivates a session too. Then it
generates the server session proof to the client.

### Step 3: Validation
The client verifies the session with the server session proof. If it succeeds,
it can continue to the 2FA authorization.
